# Round 3 — Haiku 5.5 on the text lane

**Date:** 2026-10-08 · **Question:** can `claude-haiku-5-5` replace `claude-haiku-4-5`
on the text lane (URL + Instagram caption imports, translation) without a quality
regression? · **Also:** drop prompt caching, since imports are too sporadic to ever
read a cache entry.

## TL;DR

- **Yes: switched the text lane to `claude-haiku-5-5`.** After two small prompt
  clarifications it matches or beats Haiku 4.5 on every round-2 text case:
  **13/13 schema-valid** (Haiku 4.5: 5/6 on URLs, with a recurring `steps` failure
  on the Food Network page, which Haiku 5.5 extracts cleanly).
- **About 1/10 the cost.** $0.10 / $0.50 per MTok vs $1 / $5. The newer tokenizer
  counts ~30% more tokens, so a URL import drops from ~$0.046 to **~$0.006** and a
  caption from ~$0.013 to **~$0.002** (estimated from round-2 measured Haiku 4.5
  usage × 1.3 × the new prices).
- **Haiku 5.5 reads the rules more literally.** With the unchanged production
  prompt it had two systematic gaps: (1) it ignored a yield phrased as a count
  (`kb. 8 db` → `servings: 1`), and (2) it left amount-less ingredients
  (`salt`, `olive oil`, `lime zest`) without `non_scalable_qty`. Two prompt rules
  fix both, in every run.
- **Vision lane: Haiku 5.5 is close to Sonnet 4.6, but not clean. Kept on
  Sonnet for now.** On the cookbook-matrix photos (now committed) it picked the
  right column in 6/6 runs with **0 column bleed**, a big step up from Haiku 4.5,
  which mixed all three columns. It still made small slips in 3 of 6 runs: one
  dropped ingredient, one handwritten amount misread, and one run that kept the
  crêpe-only steps. See [Stage 3](#stage-3--cookbook-matrix-photos).
- **Prompt caching removed** from the production client and the eval adapter (see
  [Caching](#caching)).

## Method

No `ANTHROPIC_API_KEY` was available in the session, so each case was run by a
**Claude Code subagent pinned to Haiku 5.5** standing in for the API call. Every
subagent confirmed it was running as `claude-haiku-5-5`.

- **Inputs:** the exact production prompts, generated by
  [`dump-prompts.ts`](dump-prompts.ts) from the round-2 case builders
  (`eval/round-2/cases.ts` → `structuringFromHtml` / `structuringFromCaption`),
  plus the real `extract_recipe` tool definition. Covers 7 Stage-1 URLs (the 6
  round-2 URLs plus Allrecipes, which fetched this time; Smitten Kitchen, Serious
  Eats and Epicurious are still blocked at fetch) and the 3 Stage-2 captions.
  Stage 3: the two cookbook-matrix photo cases (`structuringFromImage`). The
  subagent views the committed photos in send order.
- **Task given to the subagent:** read the system prompt, user message and tool
  schema in full, then output exactly the forced `extract_recipe` tool input.
- **Repeats:** URLs ×1, captions ×2, photos ×3.
- **Scoring:** strict Zod `Recipe` validation ([`score.ts`](score.ts)), then a
  field-by-field comparison against the recorded round-2 Haiku 4.5 / Sonnet 4.6 /
  Opus 4.8 outputs (`eval/round-2/runs/`), with manual review of ingredients and
  steps against the sources.
- **Outputs:** every raw output is committed under [`outputs/`](outputs/):
  `v1-prod-prompt/` (unchanged prompt) and `v2-tuned-prompt/` (after the fix).

**Caveat:** a subagent is not a raw API call. It runs inside the Claude Code
harness (its own system prompt, tool-mediated file reads, no forced `tool_choice`),
and latency and token counts are not comparable. It is a good proxy for
extraction quality, but **confirm on a few live imports after deploy**
(`ai_usage` rows: model `claude-haiku-5-5`, `ok = true`).

What stood out:

- **Follows the prompt more closely than Haiku 4.5.** Titles follow the
  4–5-word rule ("The BEST veggie lasagna" → "Veggie Lasagna", "BA's Best Chocolate
  Chip Cookies" → "Chocolate Chip Cookies"), where 4.5 and Sonnet echoed the SEO
  title. Steps are split into one action each, as the prompt asks, so step counts
  are higher. °C/°F is present on every oven step.
- **Hungarian units still correct:** `50 dkg` → 500 g, `3 dl` → 300 ml,
  `ek`/`tk` → tbsp/tsp, `gerezd` → count, `source_language: hu`.
- **Ranges are handled:** lower bound in `quantity`, full range in `notes`
  (`honey 1-2 tbsp`, `1 - 1.5 tbsp gelatine`).
- **Sections:** caption sections are preserved. The BBC cake comes back flat
  where 4.5 and Sonnet had 3 sections; the page's HTML is truncated at the 80k
  cap before most headings, so this is minor.
- **Cosmetic:** `notes` sometimes repeats the original pre-conversion amount
  (`1.5 cups` next to 150 g). This is harmless and arguably useful.

## v1 → v2: the prompt change

With the unchanged production prompt (v1, [`outputs/v1-prod-prompt/`](outputs/v1-prod-prompt/)),
all 13 outputs were schema-valid, but two things were wrong in every run:

| issue | v1 (prod prompt) | v2 |
|---|---|---|
| `Hozzávalók (kb. 8 db)` | `servings: 1` (both runs) | `servings: 8` (both runs) |
| bare `Salt`, `Olive oil`, `lime zest`, `tejföl` | `non_scalable_qty: null` | `"to_taste"`, `scalable: false` |

Haiku 4.5 and Sonnet inferred both. Haiku 5.5 applied the literal rules
("default to 1"; `non_scalable_qty` only for "ambiguous" amounts like "a
pinch"). Two rules were added to `RECIPE_JSON_SHAPE`
(`supabase/functions/_shared/ai/prompts.ts`):

```diff
 - If a quantity is ambiguous (e.g. "a pinch"), set quantity=null and
   non_scalable_qty to the matching token; scalable=false.
+- An ingredient listed with no amount at all (e.g. "salt", "olive oil",
+  "sour cream", "lime zest") is also non-scalable: quantity=null,
+  scalable=false, and non_scalable_qty="to_taste" unless a more specific
+  token fits.
-- "servings" must be a positive integer. If the source does not state
-  servings, default to 1. Never emit servings as null.
+- "servings" must be a positive integer. A stated yield counts as servings
+  in any language or form ("serves 4", "makes 12 cookies", Hungarian
+  "4 adag" or "12 db", German "für 4 Personen") — use that
+  number. Only if the source states no servings or yield at all, default to
+  1. Never emit servings as null.
```

The examples deliberately don't use the fixture's own phrasing (`kb. 8 db`), to
avoid teaching to the test. The prompt is shared with the vision lane (Sonnet 4.6);
both rules only spell out what Sonnet already did in round 2.

## Request shape changes (`client.ts`)

| change | why |
|---|---|
| text default `claude-haiku-4-5` → `claude-haiku-5-5` | this eval |
| removed `cache_control` from the system block | see [Caching](#caching) |
| `thinking: {type: 'disabled'}` on every call | Haiku 5.5 thinks by default; round 2 found thinking doesn't help extraction, and on the untooled translate call it would eat into `max_tokens`. Accepted by Haiku 4.5/5.5 and Sonnet 4.6. |
| removed the `temperature` option (translate passed 0.2) | Haiku 5.5 returns 400 on any non-default sampling parameter |
| `MAX_OUTPUT_TOKENS` 4096 → 8192 | ~30% more tokens for the same text; avoids truncating a long recipe's tool call. Only tokens actually generated are billed. |
| price row `claude-haiku-5-5` (migration `20261008120000`) | so `metrics_ai_cost` prices the new model instead of counting it as unpriced |

## Caching

Prompt caching paid off only when the same prefix was re-read within 5 minutes.
Dishton imports are one-off and sporadic, so in practice each call wrote a cache
entry at 1.25× the input price and almost none were ever read. On Haiku 4.5 the
prompt was mostly below the 4,096-token cache minimum. Haiku 5.5 lowers that
minimum to 512 tokens, which would have made **every** call pay the write premium.
Caching is now off in `client.ts` and in the round-2 eval adapter, so the eval
matches production.
